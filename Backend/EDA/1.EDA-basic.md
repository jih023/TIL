# EDA(Event-Driven Architecture) basic

## 1. EDA가 필요한 이유 
흔히 `OrderService.confirm()` 메서드를 열어보면 아래의 모습
```java
@Transactional
public void confirm(OrderId orderId) {
    Order order = orderRepository.findById(orderId);
    order.confirm();
    orderRepository.save(order);

    // 부수 효과들이 줄줄이 박혀 있음
    emailService.sendConfirmation(order);            // 이메일 발송
    inventoryService.decrease(order);                // 재고 차감
    pointService.earn(order.getUserId(), ...);       // 포인트 적립
    invoiceService.create(order);                    // 인보이스 생성
    notificationService.push(order.getUserId(), ...); // 푸시 알림
}
```

처음엔 직관적이고 깔끔해보이지만, 아래의 문제가 있음
1. 높은 결합도
- `OrderService`가 5개의 다른 서비스를 직접 import하고, 그들의 메서드 시그니처에 의존함. 한 군데가 바뀌면 다 영향을 줌.
2. 단일 책임 원칙(SRP) 위반
- `OrderService`의 책임은 "주문 확정"인데, 이메일/재고/포인트/인보이스/알림까지 다 알아야 함. 책임이 너무 많음.
3. 장애 전파
- 이메일 서버가 죽으면 -> 주문이 실패함. '나와 상관 없는 일'때문에 핵심 비즈니스가 깨짐.
4. 확장 어려움
- '추천 상품 알림 보내기'를 새로 추가하려면 `OrderService.confirm()`을 또 수정해야함. => OCP(Open-Closed Principle) 위반
5. 테스트 어려움 
- `OrderService.confirm()`을 단위 테스트하려면 5개의 의존성을 모두 Mock해야 함. 검증하고 싶은 핵심 로직(주문 확정)에 도달하기가지 setup이 산더미임.

## 2. EDA란?
Event-Driven Architecture : 시스템 컴포넌트들이 이벤트를 통해 느슨하게 통신하는 아키텍처 
```
[직접 호출 방식]
OrderService → EmailService.send()
            → InventoryService.decrease()
            → PointService.earn()
            → InvoiceService.create()

[이벤트 방식]
OrderService → "주문이 확정됐다(OrderConfirmed)" 라고 외침
                                                 ↓
                          [EmailHandler] 들었음, 이메일 보냄
                          [InventoryHandler] 들었음, 재고 차감
                          [PointHandler] 들었음, 포인트 적립
                          [InvoiceHandler] 들었음, 인보이스 생성
                          [추천 알림 Handler] 새로 들었음
```

결과
* 발생자(Publisher)와 구독자(Subscriber)가 서로를 모름 -> 느슨한 결합
* 새 기능 추가 = 새 핸들러 추가. `OrderService`는 손도 안 댐
* 장애 격리: 이메일 핸들러가 죽어도 다른 핸들러는 살아있음 

## 3. EDA의 핵심 철학
* 이벤트 = 과거에 발생한 사실(Fact)
  * `OrderConfirmed`, `PaymentCompleted`, `MemberRegistered` - 모두 과거형
  * 이미 일어난 일이므로 불변이고 취소 불가
  * '요청'이나 '명령'이 아님 - `PlaceOrder` ( X ), `OrderPlaced` ( O )
* 발행자는 구독자를 모른다
  * `OrderService`가 '누가 듣고 있나'를 신경 쓰지 않음 
  * 새 구독자가 늘어도 발행자 코드는 그대로임 
  * 단방향 흐름 
* 구독자는 독립적으로 실패 가능 
  * 이메일 핸들러가 실패해도 포인트 적립은 정상 진행 
  * 각 핸들러가 자기 책임 안에서 재시도/로깅/대응 
* 시스템을 이벤트 흐름으로 이해
  * 기존: 코드 흐름(누가 누구를 호출하나)으로 시스템 이해 -> 거대해지면 추적 불가 
  * EDA: 이벤트 타임라인으로 시스템 이해 -> '주문 확정 시 일어나는 일들'이 이벤트 핸들러 목록으로 표현됨 

## 4. EDA의 장점 
* 느슨한 결합 - 컴포넌트 간 의존성 최소화
* OCP - 기능 추가가 기존 코드 수정 없이 가능
* 장애 격리 - 한 구독자의 실패가 다른 구독자에 영향 X
* 확장성 - 트래픽 증가 시 핸들러만 독립 스케일링
* 감사 로그(Audit Trail) - 이벤트 자체가 '무슨 일이 일어났는지' 기록
* DDD와 자연스러운 결합 - Aggregate가 발행하는 Domain Event가 그대로 EDA의 이벤트가 됨 

## 5. EDA의 단점
* 흐름 파악이 어려움허 - 코드를 따라가도 이 이벤트를 누가 처리하는지가 안 보임
* 디버깅이 복잡 - 요청 하나가 여러 핸들러로 분산됨 -> 분산 추적 필요함
* 이벤트 유실 위험 - 트랜잭션 커밋 전에 이벤트가 발행되면, DB 롤백 시 이벤트만 살아남음 -> Outbox 패턴으로 해결
* 최종 일관성(Eventual Consistency) - 즉각 반영이 아니라 약간의 지연이 있을 수 있음 
* 오버엔지니어링 위험 - 단순 CRUD에 도입하면 복잡도만 증가함 

## 6. DDD + EDA = 찰떡궁합
* DDD에서 Domain Event의 역할
  * Aggregate가 중요한 상태 변화가 일어났음을 외부에 알리는 수단 
  * Ex. `Order.confirm()` 안에서 `OrderConfirmedEvent`를 발생시킴
* EDA가 Domain Event를 전달 
  * Bounded Context 내부 : Spring Application Events
  * Bounded Context 간 : Kafka, RabbitMQ 같은 메시지 브로커 (Integration Event)
  * 모놀리식이라면 Spring Application Event만으로도 EDA 패턴 구현 가능

## 7. EDA 핵심 빌딩 블록 
### 7-1. Event(이벤트)
과거에 발생한 사실(Fact)을 담는 불변 객체 

이벤트 설계 원칙
* 불변
  * 한 번 발행되면 변경 불가
* 자기 완결적
  * 처리에 필요한 정보를 이벤트 자체에 포함 (구독자가 DB를 다시 조회하지 않아도 되도록)
* 발생 시각 포함
  * `occurredAt: Instant`
* Bounded Context를 넘어가면 안 됨 
  * `UserId`를 보냈는데 구독자가 `UserName`이 궁금하다면? -> 다른 컨텍스트의 데이터를 조회하면 안 됨
  * 필요하면 이벤트에 미리 포함시키든지, 별도 인터그레이션 이벤트로 변환 
```java
public record OrderConfirmedEvent(
    OrderId orderId,
    UserId userId,
    Money totalAmount,
    List<OrderLineSnapshot> lines,
    Instant occurredAt
) {}
```

**Domain Event vs Integration Event**
| | Domain Event | Integration Event |
|---|---|---|
| 범위 | 같은 Bounded Context 내부 | 서로 다른 BC 사이 |
| 발행자 | DDD Aggregate | Application Service / Adapter |
| 전달 수단 | Spring Application Event (인메모리) | Kafka, RabbitMQ (메시지 브로커) |
| 형태 | 도메인 객체 | 직렬화된 메시지 (JSON, Avro) |
| 예 | `OrderConfirmedEvent` | `order.confirmed.v1` 토픽 |

보통 Domain Event를 만들어두고, 필요 시 Integration Event로 변환해 외부에 발행하는 패턴.

### 7-2. Event Publisher (발행자)
* 이벤트를 발행하는 주체 
* DDD 환경에선 보통 Aggregate 내부에서 이벤트를 만들고, Application Service나 Aggregate가 발행 
* Spring에선 `ApplicationEventPublisher`가 인터페이스

### 7-3. Event Bus (이벤트 버스)
* Spring Applicaton Bus
  * 같은 JVM 안에서 동작. 가볍고 빠름
* Kafka
  * 서비스 간 통신, 영속성, 대용량, 묵직하고 강력함
* RabbitMQ
  * 라우팅이 풍부함, 정교한 큐 제어
* AWS SNS/SQS, Google Pub/Sub
  * 매니지드 클라우드 옵션 

### 7-4. Event Consumer / Handler (구독자)
* 이벤트를 받아 처리하는 컴포넌트
* 하나의 이벤트에 여러 핸들러가 붙을 수 있음
* 각 핸들러는 독립적인 책임을 가짐 

### 7-5. Message Broker (인프라)
* 메시지를 중개하는 인프라 (Kafka, RabbitMQ 등)
* 발행자와 구독자 사이의 버퍼 역할
* 영속성, 재시도, 라우팅 제공 

## 8. Spring Application Bus 깊게 들여다보기 
Spring이 기본 제공하는 프로세스 내 이벤트 버스

### 8-1. 핵심 클래스
`ApplicationEventPublisher` - 발행 인터페이스
```java
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public void confirm(OrderId orderId) {
        Order order = repo.findById(orderId);
        order.confirm();
        repo.save(order);

        // 이벤트 발행 — 누가 듣는지 모름
        publisher.publishEvent(new OrderConfirmedEvent(...));
    }
}
```

`@EventListener` - 수신 핸들러 
```java
@Component
public class EmailHandler {

    @EventListener
    public void on(OrderConfirmedEvent event) {
        emailSender.sendConfirmation(event.userId(), event.orderId());
    }
}
```

* 기본 @EventListener는 호출자의 트랜잭션을 그대로 이어받아 동기 실행
* 이벤트 발행 시점에 핸들러가 곧바로 실행됨 => 트랜잭션 커밋 전에 핸들러가 끝남
* DB 저장이 실패해 롤백되어도 이메일은 이미 발송돼버림 

`@TransactionalEventListener` - 트랜잭션 단계별 실행
```java
@Component
public class PointHandler {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void on(OrderConfirmedEvent event) {
        pointService.earn(event.userId(), event.totalAmount());
    }
}
```

* phase 옵션
| Phase | 실행 시점 | 사용 케이스 |
|---|---|---|
| `BEFORE_COMMIT` | 커밋 직전 | 커밋 전 마지막 검증 |
| `AFTER_COMMIT` | 커밋 성공 후 | **가장 많이 사용**. 트랜잭션이 확실히 끝났을 때 부수 효과 실행 |
| `AFTER_ROLLBACK` | 롤백 후 | 실패 시 후처리 (보상 트랜잭션, 알림) |
| `AFTER_COMPLETION` | 커밋/롤백 무관 후 | 정리 작업 |

### 8-2. `@EventListener` vs `@TransactionalEventListener` 선택 
* `@EventListener`를 써야 할 때 
  * 호출자의 트랜잭션 안에서 같이 끝나야 하는 작업
  * 같은 트랜잭션 안에서 끝나야 하는 도메인 검증 또는 연쇄적인 도메인 변경
  * DB 감사 로그 이벤트처럼 같이 커밋되어야 일관성이 보장되는 경우
  * 트랜잭션이 없는 컨텍스트 (앱 라이프사이클, 설정 변경 등)
* `@TransactionalEventListener(AFTER_COMMIT)`을 써야 할 때 
  * 되돌릴 수 없는 부수 효과 
    * 이메일/SMS 발송, 외부 API 호출, 메시지 브로커로 발행 -> 트랜잭션이 롤백돼도 이미 나간 이메일은 회수 불가. AFTER_COMMIT으로 확실히 커밋된 후에 실행해야 함
  * 캐시 무효화, 검색 인덱스 갱신
    * 커밋 후가 자연스러운 작업 
  * 다른 시스템 동기화
    * 외부 시스템에 알릴 때 

=> 롤백돼도 되는 작업 = `@EventListener`, 롤백되면 안 되는 작업 = `@TransactionalEventListener(AFTER_COMMIT)`
* 이메일 발송 -> AFTER_COMMIT (롤백된 주문에 대해 이메일 보내면 안 됨)
* 포인트 적립 -> AFTER_COMMIT (롤백된 주문에 포인트 주면 안 됨)
* 감사 로그 -> EventListener (트랜잭션과 함께 묶여야 일관성)

## 9. EDA 구현 단계
**1. Domain Event 정의**
```java
public record OrderConfirmedEvent(
    OrderId orderId,
    UserId userId,
    Money totalAmount,
    Instant occurredAt
) {}
```

**2. Aggregate에서 이벤트 발행**
```java
public class Order {
    private final List<DomainEvent> events = new ArrayList<>();

    public void confirm() {
        require(status == OrderStatus.PENDING);
        this.status = OrderStatus.CONFIRMED;
        events.add(new OrderConfirmedEvent(id, userId, totalAmount, Instant.now()));
    }

    public List<DomainEvent> pullEvents() {
        List<DomainEvent> pulled = List.copyOf(events);
        events.clear();
        return pulled;
    }
}
```

**3. Application Service에서 이벤트 발행**
```java
@Service
public class OrderApplicationService {

    private final OrderRepository repo;
    private final ApplicationEventPublisher publisher;

    @Transactional
    public void confirm(OrderId orderId) {
        Order order = repo.findById(orderId);
        order.confirm();
        repo.save(order);

        order.pullEvents().forEach(publisher::publishEvent);
    }
}
```

**4. 독립적인 이벤트 핸들러들 정의**
```java
@Component
public class EmailHandler {
    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void on(OrderConfirmedEvent e) { ... }
}

@Component
public class PointHandler {
    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void on(OrderConfirmedEvent e) { ... }
}

@Component
public class InventoryHandler {
    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void on(OrderConfirmedEvent e) { ... }
}
```

## 10. EDA 적용 전후 비교
| 비교 항목 | Before (직접 호출) | After (EDA) |
|---|---|---|
| **의존성** | 5개의 서비스 직접 의존 | Repository + Publisher 2개만 |
| **새 기능 추가** | `OrderService` 수정 필수 | Handler 파일만 추가 |
| **장애 격리** | 이메일 실패 = 주문 실패 | 이메일 실패 ≠ 주문 실패 |
| **테스트** | 5개의 Mock 필요 | Order 단위 테스트 (Mock 0개) |
| **코드 줄 수** | 30줄 + 계속 증가 | 15줄 고정 |
| **협업** | `OrderService`가 병목 | 핸들러 파일별 독립 개발 |
| **확장 시 영향 범위** | 거대해짐 | 분산됨 |
