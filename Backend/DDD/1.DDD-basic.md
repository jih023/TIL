# DDD(Domain Driven Design) basic

## 1. 우리가 흔히 짜는 코드의 문제 
* Anemic Domain Model (빈약한 도메인 모델) 
  * `Order` 클래스를 열어보면 필드와 getter/setter밖에 없음. 즉 데이터 컨테이너(DTO)일 뿐, "주문은 어떻게 행동하는가"에 대한 로직이 전혀 없음.
  * 본질적으로 객체지향이 아니라 절차지향임. 데이터는 객체에, 로직은 서비스에 분리되어 있으니까.
  * Martin Fowler가 'Anti-pattern'이라고 명시적으로 말한 패턴임.
* Fat Service (뚱뚱한 서비스)
  * 모든 비즈니스 로직이 `OrderService`로 몰림. 한 메서드가 수백 줄, 클래스가 수천 줄까지 자라남.
  * 트랜잭션 시작 -> 검증 -> 계산 -> 외부 호출 -> 상태 변경 -> 저장이 한 메서드 안에 다 들어있음.
  * 결과적으로 무엇이 비즈니스 규칙이고 무엇이 인프라 코드인지 구분이 안 됨. 
* 로직 중복
  * '주문 시 5% 할인' 같은 규칙이 `OrderService.placeOrder()`에도, `CartService.calculateTotal()`에도, `PaymentService.confirm()`에도 각각 박혀있음. 
  * 규칙이 바뀌면 세 군데 다 고쳐야 하고, 빼먹으면 버그가 발생함.
* 테스트 어려움
  * 서비스 단위 테스트하려면 Repository, 외부 API, 메일 서비스 등 의존성을 전부 Mock 해야 함.
  * '할인 계산이 맞는지' 검증하는 테스트인데, DB Mock부터 설정하느라 시간을 다 씀.
  * 진짜 검증하고 싶은 비즈니스 규칙은 한두 줄짜리 단위 테스트로 끝나야 정상.
* 변경 전파 
  * 비즈니스 규칙 하나 바꿨는데 5개 서비스를 동시에 수정하는 상황이 발생함.
  * 변경의 비용이 점점 커지는 시스템은 결국 굳어버림(rigidty).

## 2. DDD의 핵심 철학 
* 도메인 중심 사고
  * 기술은 도메인을 표현하기 위한 수단일 뿐이고, 기술보다 비즈니스 도메인을 먼저 이해한다.
* 도메인 전문가와 개발자의 긴밀한 협업
  * PO/기획자가 말하는 '주문 취소'와 개발자가 구현한 '주문 취소'가 동일해야 함.
  * 회의실의 언어, 노션 문서의 언어, 코드의 변수명이 일치해야 함.
* 코드 = 비즈니스 문서
  * 코드를 처음 보는 사람도 비즈니스 규칙을 알 수 있어야 함.
  * 변수명 `i`, `temp`, `flag` 같은 것이 줄어들고, `RemainingStockQuantity`, `OrderConfirmation` 같은 도메인 어휘가 들어옴. 
* 모델이 곧 설계, 설계가 곧 코드 
  * '기획 문서 -> UML -> 코드'처럼 단계마다 의미가 변질되는 게 아니라, 모델과 코드가 1:1로 대응됨. 

## 3. 유비쿼터스 언어 (Ubiquitous Language)
* 도메인 전문가와 개발자가 같은 단어로 같은 것을 가리키도록 합의한 언어.

## 4. 전략적 설계 vs 전술적 설계
* 전략적 설계 (Strategic Design) - 큰 그림
  * Bounded Context: 도메인을 의미 있는 단위로 자르는 경계
  * Context Map: 각 컨텍스트가 어떻게 협력하는지 그린 지도 (경계 간의 관계 정의)
  * Ubiquitous Language: 컨텍스트마다 고유한 어휘 
* 전술적 설계 (Tactical Design) - 구현 레벨
  * Entity: 식별자가 있는 객체
  * Value Object: 값 자체로 구분되는 불변 객체
  * Aggregate: 일관성 단위의 객체 묶음
  * Repository: Aggregate의 영속성 추상화
  * Domain Service: Entity에 속하지 않는 도메인 로직
  * Domain Event: 도메인에서 일어난 사실의 알림 

## 5. DDD의 장점
* 비즈니스 로직이 도메인 모델에 집중됨
  * `Order` 객체 자신이 '내가 취소 가능한 상태인지, 환불 금액은 얼마인지'를 안다.
* 코드가 비즈니스를 직접 표현함
  * `order.cancel(reason)` 한 줄이 곧. '주문 취소'라는 비즈니스 행위.
* 테스트가 쉬움
  * 도메인 로직은 순수 객체 -> DB나 외부 의존 없이 JUnit 한 방으로 검증 가능.
* 변경에 유연
  * '취소 규칙이 바뀌었어요' -> `Order.cancel()` 한 곳만 수정.
* 팀 커뮤니케이션 향상
  * 공통 언어 덕에 PM-기획-개발 사이 통역 비용이 줄어듦.

## 6. DDD의 단점
* 학습 곡선이 높음
  * Entity, VO, Aggregate, Repository, Domain Service, Bounded Context ... 처음엔 다 비슷해 보임 ㅜㅜ
* 단순 CRUD에는 과설계
  * '공지사항 게시판'에 Aggregate Root 따지면 오히려 코드가 늘어남. 
* 도메인 전문가 협업 필수
  * 혼자 짜면 도메인 이해가 한쪽으로 편향됨.
* 초기 설계 비용
  * 장기적으로는 유지보수 비용이 줄어듦.
  * 도메인이 복잡할수록 DDD의 가치가 커짐. 

## 7. DDD 빌딩 블록 전체 지도 
| 블록 | 한 줄 설명 | 예시 |
|------|-----------|------|
| Entity | 식별자로 구분되는 도메인 객체 | Order, User |
| Value Object | 값으로 비교되는 불변 객체 | Money, Address, Email |
| Aggregate | 일관성 단위 + Aggregate Root | Order(Root) + OrderItems |
| Repository | Aggregate 단위 저장/조회 추상화 | OrderRepository |
| Domain Service | Entity에 속하지 않는 도메인 로직 | DiscountCalculator |
| Bounded Context | 모델이 유효한 경계 | 주문 컨텍스트, 카탈로그 컨텍스트 |
| Domain Event | "어떤 일이 일어났다"는 사실 | OrderPlacedEvent |

## 8. Entity
식별자(ID)로 구분되는 도메인 객체
* 속성이 바뀌어도 ID가 같으면 같은 Entity (Ex. 이메일이 바뀌어도 같은 회원)
* 생명주기가 있음: 생성 -> 변경 -> 소멸
* 자신의 비즈니스 규칙(불변식)을 스스로 지킴 
```
class Order(val id: OrderId, ...) {
    fun cancel() {
        require(status == OrderStatus.PENDING) { "이미 배송 중인 주문은 취소 불가" }
        status = OrderStatus.CANCELED
    }
}
```
`Order` 스스로 '취소 가능한가?'를 판단함. (Service X)

## 9. Value Object
값 자체가 정체정인 불변 객체
* 식별자 없음. 값이 같으면 같은 객체
* 한 번 생성 후 변경 불가 (immutable)
* 생성 시점에 자기 자신을 검증함 
```
data class Money(val amount: BigDecimal, val currency: Currency) {
    init { require(amount >= BigDecimal.ZERO) { "음수 금액 불가" } }
    operator fun plus(other: Money): Money { ... }
}
```
장점
* 원시 타입 남용 방지 (`int price` -> 단위가 원인지 달러인지 모름)
* 생성과 동시에 유효성 보장 (이후 모든 코드는 '유효한 값'이라고 가정하고 진행 가능)
* 불변이라 테스트와 동시성에 강함 

## 10. Aggregate
일관성을 보장해야 하는 객체들의 묶음
* `Order와` `OrderItem`은 따로 떨어져 존재할 수 없음. 둘이 한 묶음으로 트랜잭션 안에서 함께 변경되어야 함.
* 이 묶음이 Aggregate! 

Aggregate Root
* Aggregate에 접근하는 유일한 진입점
* 내부 객체 직접 조작 금지
* Aggregate의 불변식을 보장하는 책임자 

설계 규칙 4가지
* 외부는 루트를 통해서만 접근
  * `order.addItem(...)` ( O )
  * `order.items.add(...)` ( X )
* 한 트랜잭션에 한 Aggregate만 수정
  * `Order` 저장하면서 `Product`까지 같이 수정하지 말 것
  * 여러 Aggregate를 동시에 바꿔야 한다면 -> Domain Event로 분리 
* 다른 Aggregate와는 ID로만 참조
  * `OrderItem`이 `Product` 객체를 들고 있지 말고, `ProductId`만 들고 있어야 함.
  * 이유: 객체 참조로 들고 있으면 트랜잭션 경계가 흐려지고 메모리도 무거워짐 
* Aggregate는 작게 
  * 너무 크면 동시성 충돌과 성능 저하 

## 11. Repository
Aggregate의 영속성을 컬렉션처럼 추상화한 인터페이스
```
interface OrderRepository {
    fun findById(id: OrderId): Order?
    fun save(order: Order)
}
```
핵심 포인트
* Aggregate Root 단위로만 저장. `OrderItemRepository`는 없음.
* 인터페이스는 도메인 레이어, 구현은 인프라 레이어.
* 도메인은 '어떻게 저장하는지'를 몰라야 함 (JPA든 Mongo든 도메인 입장에선 무관)

DDD Repository vs Spring Data Repository
* DDD Repository
  * 도메인 개념. 도메인 친화적인 시그니처 (`findActiveOrdersByUser`)
* Spring Data Repository
  * 기술적 구현. `JpaRepository<Order, Ling>`

보통 도메인 인터페이스를 두고, 그 구현체 내부에서 Spring Data를 사용함.

## 12. Domain Service
특정 Entity에 속하지 않는 도메인 비즈니스 로직
* 언제 만드나?
  * 로직이 `Order`에도, `Coupon`에도, `Product`에도 속한다고 말하기 애매할 때
  * Ex. '주문 + 쿠폰 + 회원 등급을 함께 보고 최종 할인 금액 계산" -> `Order`만의 일도, `Coupon`만의 일도 아님 => `DiscountCalculator` Domain Service

* 특징
  * Stateless (상태 X, 행위만)
  * 도메인 레이어에 위치
  * 이름이 동사/행위 중심 (`TransferService`, `PricingService`)

!! Application Service와 혼동 주의 !!
| | Domain Service | Application Service |
|--|---------------|---------------------|
| 위치 | 도메인 레이어 | 애플리케이션 레이어 |
| 책임 | 비즈니스 규칙 | 트랜잭션, 흐름 조율 |
| 의존 | 다른 도메인 객체만 | Repository, 외부 API, Event 등 |

## 13. Bounded Context
같은 모델이 유효한 명확한 경계
* 같은 '상품'이라는 단어가 컨텍스트마다 다른 의미를 가짐
  * 카탈로그 컨텍스트: 이름, 설명, 이미지, 카테고리, SEO
  * 재고 컨텍스트: 수량, 창고 위치, 입출고 이력
  * 주문 컨텍스트: 가격 스냅샷, 수량, 주문 상태
  * 배송 컨텍스트: 무게, 부피, 포장 규격, 배송지 

각 컨텍스트는 독립된 Product 모델을 가져도 됨. 오히려 하나로 합치려고 하면 모델이 거대한 잡탕이 됨.
* 컨텍스트는 자체 언어, 자체 모델, 자체 DB를 가질 수 있음.
* 컨텍스트 간 통신은 명확한 인터페이스(API, Event)로 하고, 모델을 그대로 공유하지 않음.

## 14. Non-DDD 코드의 문제점 
* Order가 빈 껍데기
  * getter/setter만 가득. 비즈니스 행위 없음
* Service가 모든 걸 안다
  * 검증, 계산, 외부 호출, 알림까지 다 OrderService에서 처리 
* 다른 Aggregate를 직접 수정
  * `orderService` 안에서 `productRepository.save(product)` 호출 -> 트랜잭션 경계 붕괴 
* 원시 타입 남용
  * `int price`, `String email` -> 검증과 의미가 코드 곳곳에 흩어짐
* 테스트를 위해 Repository 전부 Mock 필요 
  * 도메인 로직이 도메일에 없고 서비스에 있으니 어쩔 수 없음 

## 15. DDD 리팩토링 단계
1. VO 추출 
* `int price` -> `Money price`
* `String email` -> `Email email`
* 가장 안전하고 효과가 큼 

2. Entity로 비즈니스 로직 이동
* `OrderService.cancel(order)` -> `order.cancel()`
* 이 로직이 진짜 Service의 일인가, 객체 자신의 일인가? 자문 

3. Service는 흐름만 조율
* 트랜잭션 시작, Repository 호출, Event 발생만 담당
* 진짜 비즈니스 규칙은 도메인 객체로 넘김 

이후엔 Aggregate 경계 재정의 -> Domain Event 도입 -> Bounded Context 분리 순으로 진화
