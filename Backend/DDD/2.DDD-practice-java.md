# DDD(Domain Driven Design) practice - java
## 📋 미션 목록 (한눈에)
 
| Step | 클래스 | 미션 요약 |
|---|---|---|
| 1-1 | `Money` | `BigDecimal amount` + `Currency` 필드 / 음수 금지 (compact constructor 검증) / 정적 팩토리 `krw(long won)` / `isPositive()` 메서드 |
| 1-2 | `CardNumber` | 숫자 16자리(`\d{16}`)만 허용 / `masked()` — 첫 4자리 + 가운데 마스킹 + 마지막 4자리 |
| 1-3 | `PaymentStatus` | `String "PENDING"/"PAID"/"REFUNDED"` → enum으로 변경 |
| 2 | `Payment` | 생성자 `(orderId, Money, CardNumber)` → PENDING으로 시작 / `pay()` PENDING→PAID + `paidAt` 기록 / `refund()` PAID→REFUNDED / 잘못된 상태 전이 시 `IllegalStateException` / 모든 필드 private, 외부 변경 불가 |
| 3 | `PaymentService` | 트랜잭션·조회·저장만 담당 (얇은 Service) / `createPayment` 생성+저장 / `pay(id)` 조회→`payment.pay()`→저장 / `refund(id)` 조회→`payment.refund()`→저장 |
 
> 공통 원칙: **before의 `PaymentService` 안에 있던 검증·상태 전이 규칙을 각 도메인 객체 안으로 이동.**

## 1. Value Object - Money
```
public record Money(BigDecimal amount, Currency currency) {

    public Money {  // ← compact constructor (괄호 없음!)
        if (amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("금액은 음수일 수 없습니다.");
        }
    }

    public static Money krw(long won) {
        return new Money(BigDecimal.valueOf(won), Currency.getInstance("KRW"));
    }

    public boolean isPositive() {
        return amount.compareTo(BigDecimal.ZERO) > 0;
    }
}
```
* VO는 불변 + 값 동등성 + 자기 검증이라는 특성을 가지고 있음
* Java 17의 `record`를 쓰면 위 3개를 쉽게 할 수 있음 
* compact constructor로 생성 시점 검증 
* 돈은 `double`로 하게 되면 부동소수점 오차로 1원씩 어긋나므로 `BigDecimal`을 써야 함.
* `BigDecimal`은 객체라서 `>`, `<`를 못 씀 -> `compareTo()` 메서드 사용

## 2. Value Object - CardNumber
```
public record CardNumber(String value) {
    public CardNumber {
        Objects.requireNonNull(value, "카드번호는 null일 수 없습니다.");
        if (!value.matches("\\d{16}")) {
            throw new IllegalArgumentException("카드 형식이 맞지 않습니다.");
        }
    }

    public String masked() {
        return value.substring(0, 4) + "-****-****-" + value.substring(value.length() - 4);
    }
}
```
* `Objects.requireNonNull()` 로 null값 검증 

## 3. Enum - PaymentStatus
```
public enum PaymentStatus {
    PENDING, PAID, REFUNDED
}
```
* `String "PENDING"` 같은 원시 타입은 오타/대소문자 실수에 무력함 
* enum으로 바꾸면 컴파일 타임에 잘못된 값을 차단함 

## 4. Entity / Aggregate Root - Payment
```
public class Payment {

    private Long id;                       
    private final String orderId;
    private final Money amount;
    private final CardNumber cardNumber;
    private PaymentStatus status;          
    private LocalDateTime paidAt;          

    public Payment(String orderId, Money amount, CardNumber cardNumber) {
        Objects.requireNonNull(orderId);
        Objects.requireNonNull(amount);
        Objects.requireNonNull(cardNumber);

        this.orderId = orderId;
        this.amount = amount;
        this.cardNumber = cardNumber;
        this.status = PaymentStatus.PENDING;
    }

    public void pay() {
        if (this.status != PaymentStatus.PENDING) {
            throw new IllegalStateException("PENDING 상태에서만 결제 가능");
        }
        this.status = PaymentStatus.PAID;
        this.paidAt = LocalDateTime.now();
    }

    public void refund() {
        if (this.status != PaymentStatus.PAID) {
            throw new IllegalStateException("PAID 상태에서만 환불 가능");
        }
        this.status = PaymentStatus.REFUNDED;
    }

    public void assignId(Long id) {
        if (this.id != null) {
            throw new IllegalStateException("id는 한 번만 할당 가능");
        }
        this.id = id;
    }

    public Long id() { return id; }
    public PaymentStatus status() { return status; }
    public LocalDateTime paidAt() { return paidAt; }
}
```
* VO는 `record`, Entity는 `class` 
* Entity는 id로 동등성 비교 
* setter 대신 도메인 행위 메서드 (`pay()`, `refund()`)
* 예외 타입 구분: `IllegalArgumentException`(인자 검증) vs `IllegalStateException`(상태 위반)

## 5. Application Service - PaymentService
```
public class PaymentService {

    private final PaymentRepository repo;

    public PaymentService(PaymentRepository repo) {
        this.repo = repo;
    }

    public Payment createPayment(String orderId, Money amount, CardNumber card) {
        Payment payment = new Payment(orderId, amount, card);
        return repo.save(payment);
    }

    public void pay(Long paymentId) {
        Payment payment = loadPayment(paymentId);
        payment.pay();
        repo.save(payment);
    }

    public void refund(Long paymentId) {
        Payment payment = loadPayment(paymentId);
        payment.refund();
        repo.save(payment);
    }

    private Payment loadPayment(Long paymentId) {
        return repo.findById(paymentId)
                .orElseThrow(() -> new IllegalArgumentException("Payment not found: " + paymentId));
    }
}
```
* Application Service는 흐름만 조율, 비즈니스 규칙은 안 들고 있음 
* 조회 -> 도메인 행위 -> 저장 흐름 
* 중복되는 payment 조회 로직은 `loadPayment` 헬퍼 추출

## 6. Before vs After 비교 
### pay() 메서드 변화 
Before (Fat Service 14줄)
```
public void pay(Long paymentId) {
    Payment payment = repo.findById(paymentId)
            .orElseThrow(() -> new IllegalArgumentException("결제를 찾을 수 없습니다: " + paymentId));

    if (payment.amount == null || payment.amount <= 0) {
        throw new IllegalStateException("금액은 0보다 커야 합니다");
    }
    if (!"PENDING".equals(payment.status)) {
        throw new IllegalStateException("이미 처리된 결제입니다: " + payment.status);
    }
    if (payment.cardNumber == null || !payment.cardNumber.matches("\\d{16}")) {
        throw new IllegalStateException("올바른 카드번호가 아닙니다");
    }

    payment.status = "PAID";
    payment.paidAt = LocalDateTime.now();
    repo.save(payment);
}
```

After (Thin Service, 3줄)
```
public void pay(Long paymentId) {
    Payment payment = loadPayment(paymentId);
    payment.pay();
    repo.save(payment);
}
```
* 검증이 사라진 게 아니라 도메인 객체로 흡수 -> 잘못된 객체는 애초에 존재할 수 없고, 잘못된 행위는 메서드 호출 시점에 막힘
