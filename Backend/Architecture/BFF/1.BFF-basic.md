# BFF(Backend for Frontend) basic

## 1. BFF란?
Backend for Frontend의 약자로, 특정 프론트엔드를 위해 만들어진 전용 백엔드를 의미한다. 
일반적인 구조에서는 여러 프론트엔드가 하나의 백엔드를 같이 사용한다. 

```
웹 ────┐
모바일 ─┼→ 공용 백엔드
관리자 ─┘
```
BFF 구조에서는 각 프론트엔드 앞에 전용 백엔드를 둔다. 
```
웹 ─────→ 웹 BFF ────┐
모바일 ─→ 모바일 BFF ──┼→ 실제 백엔드 서비스
관리자 ─→ 관리자 BFF ──┘
```

이렇게 전용 백엔드가 필요한 이유는, 웹과 모바일이 같은 상품을 보여주더라도 필요한 데이터가 다를 수 있기 때문이다. 
웹 화면에는 다음 정보가 모두 필요할 수 있다.
 - 상품 설명, 큰 이미지 여러 장, 리뷰 목록, 추천 상품, 판매자 정보

반면 모바일 화면에는 핵심 정보만 필요할 수 있다.
 - 상품 이름, 작은 이미지, 가격, 평점 

공용 백엔드가 모든 데이터를 똑같이 보내면 모바일은 필요 없는 데이터까지 받아야 한다. 
근데 BFF를 사용하면, 
```
웹 → 웹 BFF → 상세한 데이터
모바일 → 모바일 BFF → 간결한 데이터
```
처럼 각 화면에 맞게 응답을 구성할 수 있다. 

## 2. BFF의 핵심 역할 
BFF를 쉽게 말하면 프론트엔드와 실제 백엔드 사이의 맞춤형 중간 담당자이다. 
예를 들어 모바일 상품 화면에 다음 정보가 필요하다고 해보자. 
- 상품 이름은 상품 서비스에서 조회
- 재고는 재고 서비스에서 조회
- 평점은 리뷰 서비스에서 조회 

BFF가 없다면 모바일 앱이 세 서비스를 각각 호출해야 한다. 
```
모바일 → 상품 서비스
모바일 → 재고 서비스
모바일 → 리뷰 서비스
```
BFF가 있다면 모바일 앱은 한 번만 요청하고, BFF가 결과를 합쳐서 모바일 앱에 한 번에 전달한다. 
```
모바일 → 모바일 BFF
        ├→ 상품 서비스
        ├→ 재고 서비스
        └→ 리뷰 서비스
```

## 3. BFF가 해야 하는 일과 하면 안 되는 일
BFF가 주로 담당하는 일은 다음과 같다. 
- 여러 백엔드 서비스의 응답 조합 
- 프론트엔드에 적합한 데이터 형태로 변환 
- 불필요한 필드 제거 
- 프론트엔드별 API 제공 
- 인증 정보 전달 및 기본적인 접근 권한 확인 
- 캐싱, 타임아웃, 재시도 등 외부 호출 관리 
- 하위 서비스의 오류를 프론트엔드가 처리하기 쉬운 형태로 반환 

BFF는 화면에 맞는 데이터 조합과 변환을 담당하지만, 핵심 비즈니스 규칙을 소유해서는 안 된다. 
BFF에 두지 않는 것이 좋은 로직의 예 
- 할인 금액 계산
- 주문 가능 여부 판단
- 재고 차감
- 결제 승인 규칙
- 주문 상태 변경
- 회원 등급 산정 

## 4. GraphQL이란?
GraphQL은 클라이언트가 필요한 데이터의 구조와 필드를 직접 지정해서 요청하는 API 방식이다. 
REST API에서는 서버가 미리 정한 형태의 응답을 반환한다. 
```
GET /products/1
```
```
{
  "id": 1,
  "name": "키보드",
  "description": "기계식 키보드입니다.",
  "price": 40000,
  "seller": {
    "id": 20,
    "name": "키보드 상점"
  },
  "reviews": []
}
```
모바일 화면에서는 name과 price만 필요하더라도 전체 응답을 받을 수 있다. 
이때 GraphQL에서는 클라이언트가 필요한 필드만 요청한다. 
```
query {
  product(id: 1) {
    name
    price
  }
}
```
서버는 요청한 필드만 반환한다. 
```
{
  "data": {
    "product": {
      "name": "키보드",
      "price": 40000
    }
  }
}
``` 
더 많은 정보가 필요하다면 같은 API에 다른 필드를 요청할 수 있다. 
```
query {
  product(id: 1) {
    name
    description
    price
    seller {
      name
    }
    reviews {
      rating
      content
    }
  }
}
```

## 5. GraphQL 핵심 특징 
1. 필요한 필드만 요청할 수 있다. 
- 클라이언트가 원하는 필드를 직접 선택하므로 불필요한 데이터를 줄일 수 있다.
- 다음 문제 완화 가능 
    - Over-fetching : 필요하지 않은 데이터까지 받는 문제 
    - Under-fetching : 필요한 데이터를 얻기 위해 여러 API를 호출해야 하는 문제 

2. 하나의 요청으로 연관 데이터를 조회할 수 있다. 
- 상품 화면에 상품, 재고, 리뷰 정보가 필요하다고 할 때, REST 방식에서는 여러 API를 호출할 수 있다. 
    - GET /products/1
    - GET /products/1/inventory
    - GET /products/1/reviews
- GraphQL에서는 하나의 요청으로 표현할 수 있다. 
```
query {
  product(id: 1) {
    name
    price
    inventory {
      quantity
    }
    reviews {
      rating
    }
  }
}
```
GraphQL 서버 내부에서는 각 데이터를 담당하는 서비스를 호출해서 결과를 조합한다. 
```
프론트엔드
    ↓ GraphQL 요청
GraphQL 서버
    ├→ 상품 서비스
    ├→ 재고 서비스
    └→ 리뷰 서비스
```

3. 스키마와 타입이 존재한다.
GraphQL은 서버가 제공하는 데이터의 구조를 스키마로 정의한다. 
```
type Product {
  id: ID!
  name: String!
  price: Int!
  inventory: Inventory
  reviews: [Review!]!
}

type Inventory {
  quantity: Int!
}

type Review {
  rating: Int!
  content: String!
}

type Query {
  product(id: ID!): Product
}
```
클라이언트는 스키마를 통해 어떤 데이터를 요청할 수 있는지 확인할 수 있다. 

## 6. BFF와 GraphQL의 관계
BFF는 다음과 같은 역할을 담당한다.
- 여러 서비스의 데이터 조합
- 프론트엔드에 맞는 응답 구성 
- 내부 서비스 구조 숨기기 

GraphQL도 클라이언트가 필요한 데이터를 선택하고 여러 데이터를 한 번에 조회할 수 있게 한다. 
그래서 GraphQL 서버가 BFF 역할을 수행할 수 있다. 
```
웹/모바일
     ↓ GraphQL
GraphQL BFF
     ├→ 상품 서비스
     ├→ 재고 서비스
     └→ 리뷰 서비스
```

### GraphQL을 사용하면 BFF를 분리하지 않아도 될까?
- 웹과 모바일의 차이가 단순히 필요한 필드의 수라면 공용 GraphQL 서버 하나도 해결할 수 있다. 
- 하지만 다음과 같은 차이가 있다면 BFF 분리를 고려할 수 있다. 
    - 웹과 모바일의 인증 방식이 다름 
    - 각 클라이언트의 배포 주기가 다름 
    - 화면별 데이터 가공 방식이 크게 다름 
    - 장애 처리와 캐싱 정책이 다름 
    - 서로 다른 팀이 독립적으로 개발하고 운영함 
    - 모바일과 웹에서 지원하는 기능 자체가 다름
